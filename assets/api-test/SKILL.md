# 接口测试（api-test）

本地测试直接调用实际接口，**不写单元测试**。

## 触发条件

当用户说「要接口测试」「测一下这个接口」「验证接口行为」「检查接口返回」「这个接口报错了」时启用本技能。

## 交互流程（每次测试都要走）

用 `ask_user_question` 依次确认下面的选择，**不要自己替用户决定**。
该工具只支持选项（单选 / 多选），**没有数字输入框**——凡是需要数字的地方，
都要用选项给出建议值，并允许用户自己填写其它数值。

### 选择 1：测试范围（同时包含是否出图）

把「测哪些接口」和「要不要关系图」**合并在一次提问里**，别拆成两轮问：

- 某个 Controller 的**单个或多个接口**：列出该 Controller 下所有接口名让用户多选（`multi_select: true`）
- **整个 Controller 的所有接口**
- **整个 Controller 的所有接口 + 纵向关系图** ← 推荐项放第一个
- **多个 Controller**（项目里存在多个时才给）
- **全部接口（含关系图）**

项目里 Controller 超过一个时，先问"测哪个 Controller / 全部"，再问具体接口。
用户选了带图的选项后，只需再确认一次图的形态（纵向拓扑 / 横向调用链），不要重复问"要不要图"。

### 选择 2：测试次数

问每个接口跑几轮，建议选项：`1 轮（快速冒烟）` / `3 轮（推荐）` / `5 轮` / `10 轮`，
并说明用户可自行填写任意次数。

**每一轮的所有参数必须完全不同**——不是改一个值就算，要整体换一套。生成规则：

- 字符串：`<语义前缀>_<轮次>_<6 位随机>`，如 `apitest_r2_9f3a1c`
- 昵称：中文形容词 + 名词 + 轮次序号，如 `接口测试三号`
- 邮箱：`<该轮 username>@example.com`
- 手机号：`139` + 8 位随机数字（满足 `^1[3-9]\d{9}$`）
- 分页：`current` / `size` 每轮取不同组合
- 数值：在合法区间内取不同值

生成后**必须自检**：把所有轮次的参数摆在一起比对，确认没有任意两轮完全相同。
接口带唯一约束（如 username 唯一）时尤其要保证轮次之间不撞。

### 选择 3：是否导出关联关系图

若"选择 1"已经带了关系图，这里只确认**图的形态**：**纵向拓扑图**（默认，适合放进文档）/ 横向调用链。
若选择 1 没带图，就在这一步问是否要图。用户明确说不要时**不要出图**，也不要再劝。

### 选择 4：导出格式

最后问要哪些产物：`Markdown` / `Markdown + PDF` / `再加接口类与字段关系明细`。

PDF 与关系图的生成能力、以及能力不足时怎么如实告知，见《报告与产物》一节。

## 工作流程

### 第一步：确认测试目标

先询问用户要测试哪个接口。用户可能提供：

- 方法名
- Controller 类名
- 接口路径
- 消息 Topic
- RPC 接口名

目标不明确就不要猜，问清楚再往下走。

### 第二步：解析接口信息（带缓存）

在项目中定位接口定义，并按注解 / 基类识别协议类型：

| 特征 | 协议类型 |
| --- | --- |
| `@RestController` / `@Controller` | HTTP 类（RESTful、表单） |
| `@WebService` / `@WebMethod` | SOAP |
| `@DubboService` / `@GrpcService` | RPC |
| `@KafkaListener` / `@RabbitListener` / `@SqsListener` | 消息队列 |
| `@MessagingGateway` / `@ServiceActivator` | Spring Integration |
| 普通 `@Service` 方法 | 本地方法调用 |

解析时记录：接口全限定名、HTTP 方法与路径、参数列表与类型、返回值类型、关键注解、所在文件路径。

#### 缓存落盘位置（跨会话复用）

解析结果写到**项目根目录**：

```
<项目根>/.dsh-meow/api-test/cache.json
```

- 用项目根目录，不用当前工作目录：这样你用 dsh 打开项目的任意子目录，命中的都是同一份缓存。
- 项目里没有 `.dsh-meow/` 目录就用 Write 工具创建，不要因为目录不存在而放弃缓存。
- 该目录已被 meow-memory 全局忽略，不要额外动项目的 `.gitignore`。

缓存文件结构：

```json
{
  "version": 1,
  "updatedAt": "2026-10-06T00:00:00.000Z",
  "entries": {
    "<接口全限定名>#<方法名>": {
      "protocol": "http",
      "method": "POST",
      "path": "/api/user/create",
      "params": [{ "name": "req", "type": "UserCreateReq" }],
      "returns": "Result<UserVO>",
      "annotations": ["@RestController", "@PostMapping"],
      "sourceFiles": [{ "file": "src/main/java/.../UserController.java", "hash": "<sha1 或 sha256 前 16 位>", "mtime": 1760000000000 }],
      "endpoint": "http://127.0.0.1:8080/api/user/create",
      "testData": "{...}",
      "lastVerifiedAt": "2026-10-06T00:00:00.000Z",
      "lastResult": "pass"
    }
  }
}
```

`version` 是本缓存的格式版本；发现结构对不上时不要猜，直接按最新格式重建。

**复用规则（读）**

1. 先读 `<项目根>/.dsh-meow/api-test/cache.json`，按 `<接口全限定名>#<方法名>` 取条目。
2. 逐条核对 `sourceFiles` 里的 `mtime` / `hash`：
   - 全部未变 → **直接复用，不要重新解析源码**。
   - 任一变过 → 重新解析该接口，解析完回写这一条，其余条目不要动。
3. 以下情况一律重新解析，并说明原因：用户明说接口有变更、`version` 不是当前格式版本、缓存条目缺少 `sourceFiles`（无法判断新鲜度）。
4. `endpoint` 优先复用，但**正式发请求前**必须再核对一次 `application.yml` 的 `server.port` / `context-path`，端口可能被改过。

**写入规则（写）**

- **解析成功后立刻写**，不要等测试跑完——源码解析是最贵的一步。
- 每次只更新命中的那一条：先读整个文件，替换 `entries` 里对应的键，再写回，**不要覆盖其他条目**。
- 测试成功后回填 `endpoint` / `testData` / `lastVerifiedAt` / `lastResult`。
- 写 JSON 前确认语法合法，写坏一个字符会让整份缓存失效。

**其他约定**

- 项目根探测不到 `.dsh-meow/` 或项目根本身无法确认时，先问用户项目根在哪，**不要**把缓存写进 dsh 工作区的临时目录。
- 缓存文件损坏或条目残缺时，忽略残缺项并重新解析，不要把坏内容当成事实。
- `sourceFiles` 记录相对项目根的路径，方便整份缓存迁移。
- 这是本地测试，不需要写单元测试。

### 第三步：生成测试数据

根据参数类型自动构造测试数据：

- 消息类接口 → 构造消息 Payload
- RPC 接口 → 构造请求对象
- HTTP 接口 → 构造请求体 / 表单 / Query 参数

构造原则：类型正确、边界可预期、字段名与 DTO 定义一致。**避免使用真实用户数据**，用明显是测试数据的值。

### 第四步：获取实际端点

根据项目信息拼接实际测试路径：

- **HTTP / SOAP**：从 `application.yml` / `application-*.yml` 读取 `server.port` 与 `context-path`，拼接完整 URL
- **消息队列**：读取 Topic / Queue 名称与 broker 地址
- **RPC**：读取注册中心地址与服务名
- **本地方法**：通过 Spring 容器获取 Bean

配置缺失时先去找实际生效的 profile 配置，不要默认套用 `8080`。

### 第五步：检查项目启动状态

先确认项目是否已经启动好。

**如果项目没启动好，停止并提示用户启动项目或相关中间件，不要反复重试。**

判断维度：应用端口是否在监听、健康检查 / 探活端点是否响应、依赖的 broker 与注册中心是否可达。

### 第六步：发送请求并验证

按协议类型分派到对应的触发方式，然后验证结果：

- HTTP / SOAP → 发请求
- 消息队列 → 向 Topic / Queue 投递消息
- RPC → 调用对应服务
- 本地方法 → 通过 Spring 容器调用 Bean

验证内容见下方《通用测试规范》。

### 第七步：统计报错

如果报错，把报错信息整理统计出来，并明确区分两类：

- **接口本身报错**：业务异常、参数校验失败、状态码 4xx/5xx、服务端堆栈
- **连接 / 基础设施报错**：端口未监听、连接被拒、超时、认证失败、broker 不可达

两类混在一起会让用户误判根因，必须分开列出。

## 扩展选项：关联关系图

是否出图在**交互流程**的"选择 1 / 选择 3"里已经问过，这里只规定产出要求。

需要出图时，解析接口涉及的调用链（Controller → Service → Mapper → Entity → DTO）并产出：

- **调用链路图**（`digraph.mjs` 分层拓扑）——回答"请求依次经过哪些层"
- **UML 类关系图**（`classmap.mjs`）——回答"每个类有哪些字段、彼此是什么关系"
- **Mermaid `classDiagram` 源码**——可编辑、可在 GitHub 直接渲染

要求：

- 字段、方法、类型、注解**全部来自真实源码**，不允许凭印象填写
- 关系的有无与方向要回源码核对：**不画不存在的线**（例如没有继承就别画继承箭头）
- 只画与当前接口相关的链路，不要把整个工程画进去
- 同时给出关系图与关联字段说明表

## 通用测试规范

1. **状态码验证**：按协议语义验证返回状态码，覆盖成功、客户端错误、服务端错误。
2. **响应结构验证**：必填字段存在、类型正确、嵌套结构符合定义。
3. **边界值测试（只在合法区间内取边界）**：合法最小值、合法最大值、区间内的典型中间值。
   **不要为了凑用例去造代码已经显式拦掉的非法参数**——见下面「参数取值口径」。
4. **幂等性验证**：重复调用同一请求，确认结果符合接口预期（可重复执行或明确拒绝重复）。
5. **响应时间记录**：记录每次调用的耗时，标出明显偏慢的接口。
6. **异常场景**：参数缺失、权限不足等场景要有明确返回，而不是 500 或静默失败。

### 参数取值口径（重要）

测试参数**在正常（合法）范围内变更**，不要靠非法值来制造"不同"。

1. **每一轮的参数都要在业务合法区间内**，轮次之间整体换一套（见「选择 2：测试次数」）。
   "参数不同"指的是正常值不同，不是把某一轮改成空值或负数。
2. **代码已经显式校验的约束，不再单独造错误参数做用例。**
   先读代码，如果约束是显式写出来的——非空判断（`@NotNull` / `@NotBlank` / `StringUtils.isBlank`）、
   长度（`@Size` / `@Length`）、范围（`@Min` / `@Max`）、枚举取值、格式（`@Pattern` / 正则）、
   条件必填、互斥——说明这类输入在进入业务逻辑前就被拦掉了，**不生成对应的反例用例**，
   改为在报告里用一张「契约校验已覆盖」表说明：

   | 约束 | 代码位置 | 校验方式 | 处理 |
   | --- | --- | --- | --- |
   | userReq.userName 非空 | `UserServiceImpl#check` | `StringUtils.isBlank` → CustomException | 不再单列空值用例 |
   | pageSize 上限 | `BasePageRequest` | `@Max(1000)` | 不再单列超限用例 |

3. **仍然要测的"异常"**：没有显式校验的业务分支（如状态机不允许的流转、跨字段业务规则、
   权限不足、并发/重复提交）、以及代码里根本没人管的输入。这些才是真正会漏的地方。
4. **业务规则的正反两面都要有用例**（例如"只能改自己部门的单据"→ 正例 + 反例）。
5. **边界只在合法区间内取**：min / max 取**合法边界本身**，不要固定去造 `min-1` / `max+1`
   ——那类值已被上一条排除；除非该接口对越界值有专门的业务处理（如统一转成默认值），那属于业务行为，要测。

## 注意事项

- 本地测试直接调用实际接口，**不写单元测试**。
- 项目未启动时直接提示用户，**不反复重试**。
- 测试数据避免使用真实用户数据。
- 接口需要认证时，提示用户提供 Token。
- 汇报结果时区分「接口本身报错」与「连接 / 基础设施报错」，并说明本次验证覆盖了什么、没覆盖什么。
- 缓存只是加速手段：**没命中缓存也能正常工作**，不要为了省一次解析而瞎猜接口定义。
- 复用缓存前必须核对 `sourceFiles` 的新鲜度；用户说接口改过就无条件重新解析。
- 缓存写在项目根的 `.dsh-meow/api-test/cache.json`，汇报时顺带说明本次是「命中缓存」还是「重新解析」，方便用户判断结果可信度。

## 测试用例交付（每轮测试完成必做，不是可选项）

测试跑完**必须单独交付一份测试用例**给用户，不能只在报告里塞一张表就算完成。

### 用例写法参考主流做法

设计方法用业界通用的那几种，够用即可，不要发明新名词：

- **等价类划分**：每类正常取值各取一个有代表性的
- **边界值分析**：在**合法区间**内取 min / max / 典型中间值（不要造非法边界，见「参数取值口径」）
- **判定表 / 组合**：多条件互相影响时（参数 ≥ 3 且有依赖或互斥）用 pairwise，不做全排列
- **场景法 / 状态迁移**：有状态流转的业务（提交→审批→归档）按路径设计
- **业务规则正反例**：每条业务规则一条正例 + 一条反例

用例模板取常见测试管理工具（禅道 / TestLink / Excel 用例表）的列，固定为：

| 用例编号 | 所属模块 | 接口名称 | 接口路径 | 用例标题 | 用例类型 | 优先级 | 前置条件 | 测试步骤 | 测试数据 | 预期结果 | 实际结果 | 结论 |

- **用例编号**：`TC-<Controller 简称>-<3 位序号>`，如 `TC-SysUser-001`
- **用例类型**：`正向` / `业务规则` / `边界(合法)` / `异常(未被代码校验覆盖)` / `幂等` / `性能观察`
- **优先级**：`P0`（主流程）/ `P1`（重要分支）/ `P2`（次要）
- **测试数据**：写**完整可复制的值**（整段 JSON / query 串），不要写"用户名随便填"
- **预期结果**：必须能判定——HTTP 状态码 + 业务码 + data 关键字段值
- **结论**：`通过` / `失败` / `阻塞`（阻塞要写清原因）

### 交付要求

1. **先写 Markdown，再出一份 Excel**：
   - `docs/api-test-cases.md`（人看的，含用例表 + 设计说明）
   - `docs/api-test-cases.xlsx`（交给用户填/筛选的，用下面的脚本生成，**不要手写二进制**）
2. 用例表里**同时给出每轮的参数**，并标注**各轮参数互不相同**且都落在正常区间内。
3. 必须带一张 **「契约校验已覆盖」** 表（见「参数取值口径」），说明哪些非法输入因为代码已显式校验而**没有**单列用例。
4. 用例数与执行结果是两回事：用例表写清 `用例总数 / 通过 / 失败 / 阻塞`。
5. 交付时把两个文件的路径报给用户，不要只说"已生成"。

## 接口返回字段来源关系图

目标：说明接口返回结构中**每个字段**的来源——

- 字段名
- 字段含义（代码注释 / 命名可推断）
- 来源表（或来源对象）
- 查询条件（来自请求参数或代码中的固定条件）
- 层级关系（嵌套对象 / 集合要体现父子结构）

**核心原则：必须根据实际代码生成，不允许凭空编造字段来源。** 无法确定的字段标注「待确认」，不要瞎填。

### 输入信息提取

1. **接口定义**：Controller / 路由 / 视图函数，确认请求参数与返回类型。
2. **返回结构**：
   - DTO / VO / Entity 类 → 读类中的字段
   - `List<Map>` / `Map<String, Object>` → 读代码里 `put` 的 key
3. **数据来源**：Service 层的组装逻辑、Mapper / DAO / SQL、ORM 映射（MyBatis `resultMap`、JPA `@JoinColumn`）
4. **查询条件**：来自请求参数的过滤条件、代码里写死的固定条件、关联查询的 ON / WHERE 条件

### 输出结构

对象 / DTO：

```
请求参数：{"userName":"123","nickName":"123"}

返回：List<User>
├─ userName   含义：姓名        来源：user 表    条件：userName="123"
└─ dept       含义：部门集合    来源：dept 表    条件：nickName="123"
   └─ deptName  含义：部门名称  来源：dept 表    条件：nickName="123"
```

`List<Map>` / `Map<String, Object>`：

```java
Map<String, Object> result = new HashMap<>();
result.put("userName", user.getUserName());     // 来自 user 表
result.put("deptName", dept.getDeptName());     // 来自 dept 表
result.put("total", count);                     // 来自统计查询
return result;
```

```
请求参数：{"userId":"123"}

返回：Map<String, Object>
├─ userName   来源：user 表    条件：userId="123"
├─ deptName   来源：dept 表    条件：user.deptId = dept.id
└─ total      来源：统计查询    条件：userId="123"
```

嵌套 Map / List 要继续往下展开：

```
返回：Map<String, Object>
├─ user       来源：user 表
│  ├─ userName  来源：user 表    条件：userId="123"
│  └─ age       来源：user 表    条件：userId="123"
└─ deptList   来源：dept 表
   ├─ deptName 来源：dept 表    条件：user.deptId = dept.id
   └─ leader   来源：dept 表    条件：user.deptId = dept.id
```

### 生成规则

1. 只根据实际代码分析，不编造字段来源。
2. 返回结构中的**所有字段都要覆盖**，包括嵌套的对象和集合。
3. `List<Map>` / `Map` 以 `put` 的 key 为准：
   - 直接 `put("xxx", ...)` 的，字段名就是 `xxx`
   - 通过循环 `put` 的，按循环变量的语义命名
   - key 是动态拼接的，标注「动态 key，待确认」
4. 嵌套结构用缩进或层级列体现父子关系。
5. 查询条件要追溯到来源：来自请求参数的写明参数名和值；代码固定条件的写明表达式；关联查询写明关联关系（如 `a.id = b.a_id`）。
6. 无法确定来源的字段标注「待确认」，不要瞎填。
7. 格式：**Excel**（字段多、要筛选排序时最顺手）、**Markdown**（快速看）、PDF / Word（要交付归档时）。

### 交付产物与列结构

- `docs/api-test-field-source.md`：Markdown 表 + 缩进树
- `docs/api-test-field-source.xlsx`：同样用 `cases2xlsx.mjs` 生成（列多、要筛选）

建议列结构：

| 层级 | 返回字段 | 含义 | 来源表 | 查询条件 | 备注 |
|---|---|---|---|---|---|
| 1 | userName | 姓名 | user | userName="123" | |
| 1 | dept | 部门集合 | dept | nickName="123" | 嵌套集合 |
| 2 | deptName | 部门名称 | dept | nickName="123" | dept 的子字段 |
| 1 | total | 总数 | 统计查询 | userId="123" | `List<Map>` 中的 put key |

### 与调用链路图 / 类图的分工

- **字段来源关系图**（本节）：回答"这个返回值里的每个字段是从哪来的"
- **调用链路图**（`digraph.mjs`）：回答"请求依次经过哪些层"
- **UML 类关系图**（`classmap.mjs`）：回答"每个类有哪些字段、彼此是什么关系"

三者都要时各出一份，不要互相替代。

### 报告必须包含的内容

**不允许省略任何一节**，尤其接口清单与逐接口详情——用户要的是完整 API 说明：

1. **测试概览**：时间、被测工程、技术栈、测试范围、总用例数 / 通过 / 失败、总耗时
2. **运行环境**：各组件地址端口、健康检查结果、启动方式、端点拼接过程（`server.port` + `context-path` 或 broker 地址）
3. **接口清单总表**：序号 | 接口名称 | 方法 | 路径 | 说明 | 用例数 | 通过率
4. **逐接口详情**（**每个接口一节，必须包含**）：
   - 基本信息：接口名称、Controller 全限定类名、Java 方法签名、协议类型、源码文件相对路径与行号
   - 完整 API：**直连地址**与**经网关地址**（有网关时）、HTTP 方法、Content-Type、是否需要认证
   - 请求参数：逐个列出名称 / 位置(query|path|body) / 类型 / 是否必填 / 约束（长度、正则、取值范围）/ 说明
   - 返回结果：统一响应结构、data 字段的字段名 / 类型 / 说明、成功示例报文
   - 测试用例表：序号 | 参数组合（完整值）| 预期 | 实际 HTTP + 业务码 | 耗时 | 结论
   - 异常与边界：非法输入的实际返回
5. **参数变化记录**：每种接口列出每轮参数，并明确标注**各轮参数互不相同**
6. **报错统计**：按「接口本身报错」与「连接 / 基础设施报错」分类汇总
7. **测试用例**（**必出**，见《测试用例交付》）：用例表按固定列结构给全，附「契约校验已覆盖」表，
   并同时产出 `docs/api-test-cases.md` 与 `docs/api-test-cases.xlsx`。
8. **接口返回字段来源关系图**（用户要，或返回值字段 ≥ 10 个时默认给）：字段 → 来源表 → 查询条件 → 层级，
   逐字段覆盖嵌套结构，无法确定的标「待确认」（见《接口返回字段来源关系图》）。
9. **关联关系图**（用户需要时）：按下面四个子节给全，不要只丢一张图
   - **调用链路图**：按请求流向分层（网关 → Controller → Service → Mapper → Entity → DTO）
   - **UML 类关系图**：每个类分「类名 / 字段 / 方法」三栏，字段带类型与 `«PK»` `«@Version»` `«@TableLogic»` 等标记
   - **Mermaid `classDiagram` 源码**：便于用户编辑、或在 GitHub 等支持 Mermaid 的地方直接渲染
   - **关联字段说明表**：逐类列出关键字段与关联语义
10. **未覆盖部分**：明确说明哪些没测（并发、鉴权、边界外场景等），
    以及哪些"异常"因为代码已显式校验而没有单列用例（呼应「契约校验已覆盖」表）。

### 关系图的记法（参考成熟工具）

按 PlantUML 类图 / Mermaid `classDiagram` 的约定，**关系用不同箭头区分语义**，不要所有边都画成一个样：

| 记法 | 语义 | 用在本例 |
| --- | --- | --- |
| 实线 + 实心箭头 | 调用 / 委托 | Controller → Service、Service → Mapper |
| 实心菱形 + 箭头 | 组合（由…构建） | Mapper → Entity、Entity → VO、VO → PageResult |
| 空心三角 | 继承（extends） | Mapper extends `BaseMapper<SysUser>` |
| 虚线 + 空心箭头 | 依赖（作为参数） | Controller ⇢ UserCreateRequest / UserUpdateRequest |

另外要做到：
- **每条关系标注基数**（如 `1 → *`、`1 → 0..1`），并配图例说明箭头含义
- **字段必须来自真实源码**，类型、约束、`@Version` / `@TableLogic` 这类关键注解都要标出来，不要凭印象杜撰
- **不要画不存在的线**：没有继承关系就不要画继承箭头；关系方向要核对（谁依赖谁、谁由谁构建）
- 图宽控制在 **740px 以内**能放进一页 A4；类多时用更大的画布并接受整体缩放
- **类数超过 24 个会自动进入紧凑模式**（只保留类名 / 构造型 / 包名，省略字段与方法栏），
  否则每个类的字段全展开会让画布大到不可读。可强制：`"compact": true|false`，阈值 `"compactThreshold": N`。
  大系统建议**按模块分多张图**，不要硬塞一张
- **图里有环是正常的**（双向依赖、回调、互相引用的 DTO），生成器会自动打破环以保持分层，
  并输出 `broke N dependency cycle(s)`。这条提示说明分层仍然有效，不是错误
- 宽度上限用 `"maxWidth"` 调整（默认 1480px）；超出时生成器会告警并指出是哪一层超宽

### 用脚本生成 PDF、用例表与关系图

本技能自带四个零依赖脚本（`assets/api-test/scripts/`，路径由技能的 `Base directory` 决定）：

```powershell
# Markdown -> PDF（内部用 Chrome/Edge headless 打印，中文字体已适配）
node "<base>/scripts/md2pdf.mjs" <报告.md> [输出.pdf]

# 用例表 / 字段来源表 -> 真正的 .xlsx（多 sheet、表头加粗冻结、自动筛选）
node "<base>/scripts/cases2xlsx.mjs" <用例.json> <输出.xlsx> [--csv]

# 调用链路图 -> SVG（自算分层布局，无需 Graphviz / Java / mermaid）
node "<base>/scripts/digraph.mjs" <图描述.json> <输出.svg>

# UML 类关系图 -> SVG（类框分栏显示字段与方法，关系带箭头语义与基数）
node "<base>/scripts/classmap.mjs" <类图描述.json> <输出.svg>
```

`cases2xlsx.mjs` 的输入格式（用例表与字段来源表共用同一个脚本）：

```json
{
  "title": "接口测试用例",
  "sheets": [
    {
      "name": "测试用例",
      "columns": ["用例编号", "所属模块", "接口名称", "接口路径", "用例标题", "用例类型", "优先级", "前置条件", "测试步骤", "测试数据", "预期结果", "实际结果", "结论"],
      "rows": [["TC-SysUser-001", "用户管理", "SysUserController#create", "/api/users/create", "新增用户-正向", "正向", "P0", "已登录", "1. POST 创建\n2. 核对返回", "{\"userName\":\"apitest_r1_9f3a1c\"}", "HTTP 200；code=200；data.id 非空", "HTTP 200 / 18ms", "通过"]],
      "widths": [16, 12, 26, 22, 30, 22, 8, 28, 30, 60, 34, 24, 8]
    },
    { "name": "契约校验已覆盖", "columns": ["约束", "代码位置", "校验方式", "处理"], "rows": [["userReq.userName 非空", "UserServiceImpl#check", "StringUtils.isBlank → CustomException", "不再单列空值用例"]] }
  ]
}
```

说明：

- `sheets` 可给多个；只给单个 `{ columns, rows }` 也可以。
- 每个字符串都按**文本**写入（`inlineStr`）：`=1+1`、`00123`、`2026-10-11` 不会被 Excel 当成公式/数字/日期改写，
  数字与布尔值保持真实类型以便排序求和。
- 超过 Excel 单元格上限（32767 字符）会自动截断并在 stderr 告警；sheet 名里的 `: \ / ? * [ ]` 会被替换。
- 加 `--csv` 会在 xlsx 旁边再写每个 sheet 的 UTF-8 BOM CSV，方便其它工具读。
- **不要手写 xlsx 二进制，也不要把用例只写成 Markdown 表**——用户要的是能直接打开筛选的文件。

`classmap.mjs` 的输入格式：

```json
{
  "title": "SysUserController UML 类关系图",
  "classes": [
    {
      "id": "SysUser", "name": "SysUser", "package": "com.example.user.entity",
      "stereotype": "TableName(sys_user)", "color": "entity",
      "fields": [{ "name": "id", "type": "Long", "marker": "PK", "note": "IdType.AUTO" }],
      "methods": ["static from(SysUser): UserVO"]
    }
  ],
  "relations": [
    { "from": "SysUserMapper", "to": "SysUser", "type": "composition", "label": "映射结果", "cardinality": "1 → *" }
  ]
}
```

`color` 取 `controller` / `service` / `mapper` / `entity` / `dto` / `other`；
`relations[].type` 取 `call`（实线箭头）/ `composition`（实心菱形）/ `inheritance`（空心三角）/ `dependency`（虚线箭头）；
`fields[].marker` 是自由文本徽标（`PK` `@Version` `@TableLogic` `必填` 等），脚本会自动配色。

`digraph.mjs` 的输入格式：

```json
{
  "title": "SysUserController 关联关系图",
  "layout": "vertical",
  "nodes": [{ "id": "C", "label": "SysUserController", "sub": "/api/users", "kind": "controller" }],
  "edges": [{ "from": "C", "to": "S", "label": "调用" }]
}
```

`kind` 取 `controller` / `service` / `mapper` / `entity` / `dto` / `other`，决定配色。
`layout` 默认 `vertical`（适合放进 PDF 一页）；链路很长且用户要"横向调用链"时用 `horizontal`。
生成的 SVG 用 `![](api-test-graph.svg)` 引用进 Markdown，再交给 `md2pdf.mjs` 就会一起打进 PDF。

### 能力边界（做不到就如实说，不要假装成功）

| 能力 | 现状 | 缺什么时的做法 |
| --- | --- | --- |
| Markdown | 内置支持 | — |
| PDF | **靠本机 Chromium 内核**（Chrome 或 Edge）。脚本会自动探测常见路径，也可用环境变量 `DSH_PDF_BROWSER` 指定 | 两者都没有时**明确告知用户**："本机没有 Chrome/Edge，无法生成 PDF，请安装其一或改用 Markdown"，不要伪造 PDF |
| 关系图 | **自带两个 SVG 生成器**：`digraph.mjs` 画调用链路、`classmap.mjs` 画 UML 类图（字段/方法/关系语义），无需任何外部依赖 | 想要 Mermaid 源码就另存一份 `.mmd`（报告里也会贴出源码块，GitHub 等能直接渲染） |
| 用例表 / 字段来源表 | **`cases2xlsx.mjs` 生成真正的 .xlsx**（零依赖，多 sheet、冻结表头、自动筛选），也可同时出 CSV | 用户要 Word 时用 Markdown 转，不要谎称生成了 .docx |
| Graphviz / Java 渲染 | 不依赖 | 不要假设本机有 `dot` / `plantuml`；需要时先探测再决定 |

**验证产物真的生成了**：检查文件存在且非空（PDF 还要确认文件头是 `%PDF-`），
再把路径报给用户。生成失败要给出具体原因，不要只说"已完成"。

### 交付前自检（这几点都实际踩过坑）

1. **文件存在 ≠ 内容正确**：PDF 要确认文件头是 `%PDF-`；报告要抽查章节数、用例行数。
2. **确认图真的进了 PDF**：Chrome 打印时**不会加载页面引用的本地 `file://` 图片**，
   报告里的 `![](...svg)` 会导致 PDF 里完全没有图。`md2pdf.mjs` 已改为把本地 SVG
   **内联**进 HTML，但你要复核：看 **PDF 页数是否随加图而增加**，或看生成的 HTML 里
   `<figure class="diagram">` 的数量。**不要用 PDF 里有没有 `/Subtype /Image` 判断**——
   矢量图不产生该资源，会误判成"没嵌进去"。
3. **图里不能有"示意 / 占位"内容**：图为事实陈述。曾在类图 spec 里留过一条
   "占位：无继承关系"，结果被如实画成一条**实际不存在的继承箭头**。交付前必须清掉
   一切 placeholder，并回源码核对待画关系的有无与方向。
4. **失败要如实说**：能力缺失就明确讲缺什么、怎么补，**不要伪造产物**，也不要把
   "命令跑完了"当成"结果正确"。
5. **生成图之前，先用真实规模的数据自测一遍生成器**（这条来自一次真实翻车）：
   只用「空列表 / 单节点 / 自环」这类玩具输入测，会全部通过却漏掉致命缺陷。
   最少要覆盖：

   - **节点数按真实规模**（几十个类、5 层以上），不要只放 9 个
   - **存在环与双向关系**（双向依赖、回调、互相引用的 DTO）——真实工程里很常见
   - **超长标签**（长类名、长泛型、长注解）与特殊字符
   - 超宽/超长时的画布尺寸，是否还放得进文档

   自测的正确做法：**不要只看退出码是不是 0**，要检查实际产物——数一数节点是否真的分布
   在不同层（而不是全挤在一层）、画布宽高比是否合理、有没有重叠。曾经就是「退出码 0、
   校验全绿」，但所有节点静默塌进同一层（60 个类产出 42982×383 的画布）才发现分层算法
   在**环图**上完全失效。
6. **改完脚本先 `node --check`**：四个 .mjs 都是独立可执行脚本，语法错误会让技能在
   真正要出图/出表时才失败。改完立刻 `node --check <脚本>` 再跑一次真实 spec。
   `cases2xlsx.mjs` 改完还要跑 `node verify-cases.mjs`（在插件根目录）：它用 64 条用例、
   5 个 sheet 的真实规模数据生成一次，再把产物**从字节里解回来**核对单元格内容
   （公式样式文本、前导零、日期样式文本、超长截断、空值、非法 sheet 名、CSV 引号转义）。
   **不要只看退出码，也不要用"能打开"当作"内容对"**——要抽查具体单元格的值。
7. **xlsx 交付前抽查**：用 `cases2xlsx.mjs` 生成后，至少确认 sheet 名、行数、表头文字与
   几条典型用例的数据列；文件存在不等于内容正确。
